## What

Add `GET /original/:id` and `GET /thumb/:id` to the sidecar for **web formats only** (jpg/jpeg/png/webp/gif/bmp). `/original` streams the resolved local file; `/thumb` serves the persisted thumbnail (using `getThumbnailPath` resolution) and generates it with Sharp server-side if missing. Both send `Cross-Origin-Resource-Policy` headers so images load under the page's COEP. This completes the Phase A end-to-end path: gallery + thumbnails + full-size view for common formats.

## Why

Browsers cannot load `file://`; the server must stream bytes. Thumbnails already persist to disk and can simply be served (regenerated with Sharp when absent). See [INV-034](../investigations/INV-034_MEDIUM_OTHER_headless-sidecar-web-build.md) (Requirements 4, 6, 10; Blast Radius 5, 6, 7).

## Implementation Steps

- [ ] 1. Create `src/server/routes/images.ts`. `GET /original/:id`: resolve id→path via `path-resolver` (TASK-128), assert the extension is a web format, stream the file with correct `Content-Type`, `Cross-Origin-Resource-Policy: same-origin` (or `cross-origin` as the deployment needs), and caching headers. Reject non-web formats with a hint to use `/preview` (TASK-131).
- [ ] 2. `GET /thumb/:id`: compute the thumbnail path via `getThumbnailPath(absolutePath, thumbnailDir)` (reuse `common/fs.ts`). If it exists, stream it. If not, generate it with **Sharp** (resize to `thumbnailMaxSize`, encode to the existing `thumbnailFormat`), persist to the same path, then stream. Send CORP headers.
- [ ] 3. Create `src/server/thumbnails.ts` wrapping Sharp generation so TASK-131 can extend it for decoded formats.
- [ ] 4. Ensure `HttpBackend.encodeFilePath` / the web seam URLs (TASK-127) match these route shapes so the gallery and viewer request the right URLs.
- [ ] 5. Verify masonry layout still works in the browser (SharedArrayBuffer requires COOP/COEP from TASK-128 + CORP here).
